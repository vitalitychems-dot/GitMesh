# Local vault CLI

An offline-first Node.js command-line project for keeping local JSON records and moving snapshots between machines with Git bundles. The vault CLI opens no network ports and has no third-party runtime dependencies. A separate, explicitly run source-sync script can publish only allowlisted source files.

## Run

From the GitMesh repository root:

```sh
node projects/local-vault/gitmesh-ultimate-core.mjs
```

Or use the launcher in this folder: `run-mesh.bat` on Windows, or `sh run-mesh.sh` on macOS/Linux. On iPhone/iPad, this is not a native app and cannot auto-run when downloaded; shell support depends on compatible Node.js and Git being available.

Requirements: Node.js 20 or newer, Git on `PATH`, and an interactive terminal.

On first launch, choose an initial admin sigil of at least 12 characters. Later launches ask for it without echoing it. After a successful sign-in, GitMesh displays a new, randomly generated sigil once. Save it, then type `SAVED` to activate it and open the console. The prior sigil is invalidated when the replacement is saved. If you cancel instead, the prior sigil remains valid and the console stays locked.

The local credential file stores a salted scrypt verifier and hashes of consumed sigils, never the active sigil itself. Generated sigils use a persistent increasing generation number and are checked against the consumed-key history to prevent reuse. The menu can also set a new sigil; prior sigils cannot be reused. There is no in-app recovery if the active sigil is lost. Existing version-1 passphrase verifier files are accepted and migrate to rotating sigils on the next successful sign-in.

## Local data

Runtime data lives under `projects/local-vault/SovereignMeshVault/`:

- `ledger_matrix/` — local JSON records.
- `drops_inbound/` — bundles available for manual import.
- `bundles_outbound/` — exported bundles.
- `active_sigil.hash` — local verifier, rotation counter, and hashes of consumed sigils.

The `.gitignore` in this folder excludes the entire vault from the public repository. The source code and documentation are intended to be committed; runtime records, credentials, and bundles are not.

## Behavior and limits

- Checks each record's SHA-256 checksum when listing or importing it.
- Imports only a bundle explicitly selected from `drops_inbound`; it does not watch folders or execute incoming content.
- Limits the ledger to 1,000 records and imported bundles to 100 MiB.
- Does not sync, publish, or push local data to GitHub.
- The separate source-sync script sends only the CLI source, README, and sync script to `vitalitychems-dot/GitMesh`; it never reads or uploads `SovereignMeshVault/`.
- Rotates the admin sigil after each successful sign-in; the replacement is displayed once and must be saved before access is granted.
- A restored older copy of the local vault can restore an older sigil verifier and rotation history. Protect backups and avoid restoring stale copies if you need to keep prior sigils permanently invalid.

The scrypt verifier is local access control, not device encryption or account authentication. The sigil is shown in the terminal once per rotation, so store it somewhere secure. A checksum can detect accidental changes but is not a digital signature. Git bundles are unencrypted and readable by anyone who obtains them. File deletion cannot guarantee forensic erasure on SSDs, filesystems with journals, backups, or snapshots. Keep secrets and sensitive personal data out of records unless you have separately assessed the storage and transfer risks.

## Sync source to GitHub

For one offline check of the allowlisted source files, run `node ./sync-public-source.mjs --check-local`. It checks for credential-like values in all three source files and validates JavaScript syntax in both `.mjs` files. It needs no `GITHUB_TOKEN`, makes no network requests, and does not publish. Failures show only safe filenames and line or column numbers, never credential values, source lines, or raw Node diagnostics.

This is separate from vault data transfer and makes an outbound HTTPS request to GitHub. On Replit, store a fine-grained token as the `GITHUB_TOKEN` Secret, limited to the `vitalitychems-dot/GitMesh` repository with Contents write access. Replit Secrets are project-level and available to processes running in the project; they are not folder-scoped. The sync script reads the token from `process.env.GITHUB_TOKEN` only when run and never writes or prints it.

Run from this folder with `node ./sync-public-source.mjs`. To scan the allowlisted source files locally before configuring GitHub access, run `node ./sync-public-source.mjs --check-credentials`; it needs no `GITHUB_TOKEN`, makes no network requests, exits nonzero when it finds a credential-like value, and reports the affected filename and line number without revealing the credential or source line. To check only allowlisted JavaScript syntax, run `node ./sync-public-source.mjs --check-syntax`; it needs no `GITHUB_TOKEN`, scans only `.mjs` files, does not check for credential-like values, makes no network requests, and reports safe filename and numeric line/column details on syntax errors without showing parser diagnostics or source. Before any GitHub request, a normal sync validates the local source files and runs the full mocked security regression suite. The suite's raw output is suppressed; on failure, sync reports only allowlisted test names or a sanitized Python version/start/timeout status, plus a command to reproduce the checks locally. Sync stops without contacting GitHub. This preflight requires Python 3.9 or newer, Node.js 20 or newer, and Git on `PATH`. It also checks each allowlisted `.mjs` file with Node's syntax checker and suppresses diagnostics so source lines are not printed. It compares the three fixed source paths with `main`, creates no commit if they already match, and uses a non-force ref update when changes are needed. After a successful sync, it reports only the changed allowlisted file paths. To inspect the planned paths without publishing, run `node ./sync-public-source.mjs --dry-run`; this performs the same preflight, then read-only GitHub comparisons and makes no GitHub changes. If `main` advances during the first comparison, the preview retries once using the newly fetched full commit SHA, then checks that `main` stayed at that snapshot. If it advances again or a request fails, the preview stops and asks you to rerun the dry run; it never makes GitHub changes. Do not put the token in a `.env` file, source file, Git remote URL, or command-line argument.

By default, source sync targets `main`. To preview or sync another branch, pass `--branch <name>`; the option can appear before or after `--dry-run`. For example, preview with `node ./sync-public-source.mjs --dry-run --branch release/2026.10`, or sync with `node ./sync-public-source.mjs --branch release/2026.10`. Branch names must use up to 255 printable ASCII characters and cannot contain spaces, begin with a hyphen, or contain invalid Git ref components. Invalid names are rejected before GitHub requests; valid names are URL-encoded in the ref route. Branch updates continue to use a non-force ref update.

To add an optional local pre-commit check, run the command matching your repository layout:

- **GitMesh inside the Replit workspace:** from the workspace root, run `node gitmesh-template/install-pre-commit-hook.mjs`.
- **GitMesh as the repository root:** from that repository's root, run `node ./install-pre-commit-hook.mjs`.

To inspect the active setup without changing Git configuration, add `--status` to the matching command. The diagnostic identifies repository-local, worktree-local, and shared settings, reports when GitMesh is inactive, and prints a scope-specific disable command. For a chained setup, that command removes the selected setting and its dispatcher files only after verifying the GitMesh marker and recorded file inventory.

By default, the installer refuses an existing `core.hooksPath` or custom files in Git's default hooks directory, and leaves their files and settings unchanged. To explicitly run existing hooks with GitMesh, add `--chain-existing` to the matching installer command above. This creates a dispatcher in the current Git directory, calls the existing executable pre-commit hook first, and runs the GitMesh staged source checks only if the existing hook succeeds. The checks scan staged credentials and validate staged JavaScript syntax. For pushes, an existing executable pre-push hook also runs first; GitMesh receives the same ref list for its optional scan. Other executable hooks are forwarded to their original files. Existing hook files and earlier `core.hooksPath` values are left unchanged; the installer appends a setting only at the selected repository or worktree scope and prints a matching `--disable-chain` command. Run the printed command to remove that setting and the dispatcher directory. New dispatchers record an exact file inventory and content hashes; cleanup refuses unmarked, altered, or unexpected contents. Older marker-only dispatchers are accepted only when every contained hook file has the GitMesh dispatcher header. The cleanup never deletes the original hooks or changes global or sibling-worktree settings.

Without `--chain-existing`, if the installer finds a repository-local hook, it prints the layout-correct command to add to that hook: `node gitmesh-template/sync-public-source.mjs --check-staged-credentials` in the workspace layout, or `node ./sync-public-source.mjs --check-staged-credentials` when GitMesh is the repository root. That command checks credentials in staged allowlisted source and validates the syntax of staged `.mjs` files. If the installer finds a shared hooks path, use the opt-in dispatcher or a repository-specific wrapper; do not change the global setting.

In a linked worktree, the default command still refuses. To opt in for just that worktree, append `--worktree-local` to the matching command above; to chain existing hooks there, use both `--worktree-local --chain-existing`. This requires the repository to already have `extensions.worktreeConfig=true`; the installer writes `core.hooksPath` with Git's worktree scope and does not enable that shared extension or modify sibling/global hook settings. For a non-chained setup, the hooks path is relative to the worktree root, so it remains valid when the worktree is relocated with `git worktree move`. For a chained setup, the dispatcher stays in the selected worktree's Git metadata, and GitMesh plus custom hooks inside that worktree are resolved from its current root, so they remain active after a move. When GitMesh is the repository root, the configured path is `hooks`. If the extension is not enabled, a repository maintainer can enable it deliberately with `git config --local extensions.worktreeConfig true`; this changes repository-wide Git configuration behavior, so do so intentionally. The installer prints the scoped `--worktree-local --disable-chain` command to remove its dispatcher setting and files after validation. Without `--chain-existing`, the setup refuses existing hooks or unsupported worktree configurations without writing settings.

The outgoing-commit credential check is optional and disabled by default. After installing the GitMesh hook path, enable it for this repository with `git config --local gitmesh.prePushCredentialCheck true`; disable it with `git config --local --unset gitmesh.prePushCredentialCheck`. When enabled, it scans outgoing commits locally for credential-like values in the three allowlisted source files, requires no `GITHUB_TOKEN`, makes no network requests, and blocks a push with only file paths and line numbers. It does not change the pre-commit check. Local hooks can be bypassed with `git push --no-verify`, so this is not server-side enforcement.

When one of the three allowlisted source files is staged, the hook first checks that Node.js 20 or newer is available, then scans staged contents for credential-like values without requiring or reading `GITHUB_TOKEN` or making network requests. Clean staged sources pass, and unrelated staged files are not scanned. If Node.js is missing or older than 20, install or upgrade Node.js to 20 or newer, ensure `node --version` reports `v20` or newer, and retry the commit; the hook blocks before inspecting staged content. If a staged Git command times out, check whether another Git process is stuck and whether the repository responds to Git commands, then retry; the scan fails closed without displaying Git diagnostics, staged content, or credentials. If Git reports an unreadable staged index, resolve that index issue, stage the intended file state again, and retry. Git's standard `git commit --no-verify` behavior can skip local hooks; no GitMesh sync flag disables the independent credential scan that runs before publishing.

The staged source scan uses a 15,000 ms (15-second) timeout by default. To accommodate slower repositories, maintainers can set `GITMESH_STAGED_SCAN_TIMEOUT_MS` in the environment that runs Git (for example, `export GITMESH_STAGED_SCAN_TIMEOUT_MS=30000`) to a whole-number value from 1,000 to 120,000 milliseconds (1–120 seconds). Values outside that range or non-integer values fail closed and block the commit; they do not disable the timeout.

If GitHub rejects a sync, the error message gives a safe next step without printing the token, authorization header, or request body:

- **Authentication rejected:** Check that the `GITHUB_TOKEN` Secret is current and has access to `vitalitychems-dot/GitMesh`.
- **Access denied:** Check repository access and the required Contents permission (read for lookups, write for updates).
- **Rate limit:** Wait for the limit to reset, then retry.
- **Network or temporary GitHub error:** Check the connection, wait briefly, and retry.
- **Branch conflict:** Review `main` and retry after resolving the conflict. Sync never force-updates the branch.

## Security regression checks

The regression harness is maintained in the Replit workspace and is not included in the GitHub source sync. The sync preflight checks for `tests/test_security_regressions.py` alongside the workspace copy of this script before running Python. If it is missing, restore it from a complete GitMesh workspace and rerun sync; the error includes the local reproduction command and confirms GitHub was not contacted. If Python cannot start, install or upgrade to Python 3.9 or newer and make `python3` available on `PATH`, then rerun the regression checks and sync. If the installed version is too old, the error reports the detected major and minor version and gives an upgrade step without forwarding Python's raw output. Reproduce the checks from the workspace root with `python3 gitmesh-template/tests/test_security_regressions.py`. The checks use a disposable fixture and a mocked GitHub API; they do not read the active vault or make network requests. Python 3.9 or newer, Node.js, and Git must be available.
